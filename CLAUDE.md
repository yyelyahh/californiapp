californiapp — contexto do projeto

Mini-ERP de revenda (estoque, vendas, consignação com vendedores) que está sendo estendido com uma camada de e-commerce por vendedor (catálogo público + carrinho + checkout via WhatsApp + fidelidade).

Stack
Frontend: React + Vite + TypeScript + shadcn/ui + Tailwind. Lib de animação motion já instalada.
Backend: 100% Supabase (Postgres + Auth + RLS + Postgres functions). Não existe servidor próprio — o front fala direto com o banco via supabase-js, e regras de negócio críticas ficam em funções Postgres (SECURITY DEFINER), não só no cliente.
Editor principal do dono do projeto: Lovable (ele não programa diretamente; pede mudanças em linguagem natural e revisa o diff antes de aprovar). Ele tem acesso a VS Code também, mas prefere trocar em linguagem natural — ao propor mudanças, dê o trecho exato de código (antes/depois) e o caminho do arquivo, não só a ideia.
Migrations ficam em supabase/migrations/, aplicadas via Lovable ou direto no SQL Editor do Supabase.
Arquitetura de dados relevante
products: uma linha por sabor (não por modelo). Colunas: brand, model, flavor, sale_price, stock, purchase_price (oculto de authenticated via GRANT por coluna — cuidado ao adicionar coluna nova nessa tabela, ver Gotchas).
product_assignments: quanto de cada produto está atribuído a cada vendedor (consignação). UNIQUE (seller_id, product_id) — uma linha por par, garantido pelo banco. Antes disso quem consolidava era só o client, e duas linhas do mesmo par faziam o sabor aparecer duplicado no catálogo com estoque menor que o real.
sales: ledger de vendas confirmadas. Nunca inserido direto pelo client — sempre via function create_sale (atômica).
orders / order_items: pedidos feitos pelo catálogo público (/loja/:sellerId). Status: pendente / confirmada / recusada / expirada. Recusada é decisão do vendedor; expirada é ninguém ter respondido dentro do prazo — são separados de propósito: é o que permite saber se venda está sendo perdida por demora. order_items.sale_id só é preenchido quando o pedido é confirmado (vira uma linha em sales de verdade). FK com ON DELETE SET NULL — se a venda for deletada depois, o vínculo cai sozinho.
order_items.unit_price é gravado a partir de products.sale_price lido dentro da function, NUNCA do que o cliente mandou. create_pending_order é GRANT ... TO anon: nada que venha daquele payload é fonte de verdade de dinheiro. O front manda só product_id e quantity — o unit_price que ele mandava "por compatibilidade" saiu, porque fingia que o carrinho tinha voz no preço. Um pedido pode ter DUAS linhas do mesmo produto: a unidade premiada pela fidelidade vira linha própria, com o preço descontado (ver Fidelidade). order_items não tem unique em (order_id, product_id) de propósito, e confirm_order percorre item a item repassando unit_price para create_sale, então cada linha vira uma venda com o valor certo.
customers: cadastro por WhatsApp (chave única, normalizado — só dígitos, sem formatação).
product_model_images: foto por marca+modelo (não por sabor) — todos os sabores do mesmo modelo compartilham a mesma foto. É a ÚNICA fonte de foto: quem lê é get_seller_catalog, que casa marca+modelo com lower(btrim(...)) dos dois lados. Quem grava é o ModelImagesDialog (aberto em Produtos), mas NUNCA direto na tabela — a escrita passa por set_model_image(p_brand, p_model, p_image_url), que normaliza a chave do MESMO jeito que a leitura, apaga tudo o que casa e deixa uma linha só (URL vazia = remover a foto). Enquanto a tela gravava e apagava por igualdade exata, remover a foto de "Ignite" não alcançava a linha gravada como "ignite": a tela dizia "Foto removida" e a loja continuava mostrando. Índice único em (lower(btrim(brand)), lower(btrim(model))) garante a linha única no banco; o desempate por created_at DESC continua escrito na função, mas não tem mais o que desempatar. products.image_url existe, é resíduo de antes e ninguém escreve nele — serve só de fallback para modelo sem foto cadastrada. Não volte a ler foto de lá: a loja monta o card do modelo com firstModelImage, que pega o primeiro sabor COM imagem na ordem (brand, flavor), então um único sabor com url velha mandava na foto do modelo inteiro. A tabela nasceu no SQL Editor e ficou tempo demais sem migration: como o corpo de uma function é validado no CREATE (check_function_bodies), banco novo parava na 20260909140000 com relation "public.product_model_images" does not exist e derrubava todas as migrations seguintes. Hoje ela é criada ali mesmo, no topo do arquivo, com IF NOT EXISTS. Tabela criada no SQL Editor tem que virar CREATE TABLE IF NOT EXISTS na primeira migration que a mencionar, senão só o banco vivo funciona.
Fluxo da loja pública (/loja/:sellerId)
Cliente abre o link do vendedor e cai direto no catálogo. A identificação mora no CHECKOUT, não na porta: o link chega pelo WhatsApp e muita gente abre só pra olhar — pedir telefone antes de mostrar preço perde essa pessoa na primeira tela.
Catálogo agrupado por modelo (cards com foto/bloco de cor placeholder), popup/tela cheia com animação motion (layoutId) pra escolher sabor.
Acima da busca fica o trilho de avisos (StoreNotices): cards compactos com o próximo aparecendo pela borda, trocando sozinhos a cada 3s e NO TOQUE — nunca no arraste, porque a tela já rola na vertical e um trilho arrastável rouba esse gesto. Hoje são dois: a promoção do combo (só aparece com as regras carregadas — card que anuncia promoção sem dizer o tamanho dela não vale a tela) e o aviso do botão "i". Esse botão fica ao lado do carrinho, com o mesmo desenho, e abre o sheet Tira-dúvidas (64vh, só leitura): fidelidade, combo, como o pedido é confirmado, pagamento e "o preço não muda depois de enviado". As respostas com número saem de get_store_rules — resposta que precisa de número não aparece sem as regras, em vez de sair com buraco no meio.
Adiciona ao carrinho (nada vai pro banco ainda) → abre o checkout → digita o WhatsApp, que dispara get_customer_loyalty (com 350ms de debounce: número de 11 dígitos ficava completo aos 10 e de novo aos 11, e consultava duas vezes): se acha cadastro mostra o cartão de fidelidade e nem pergunta o nome; se não acha, pede o nome e mostra a regra do desconto — pra quem ainda não é cliente a fidelidade era invisível, e é justamente ele que ela precisa convencer.
Carrinho e telefone sobrevivem ao reload (localStorage: carrinho por vendedor, validade de 7 dias; telefone global, é da pessoa e não da loja). O que volta do storage NÃO é confiado: um efeito reconcilia o carrinho contra o catálogo recém-lido — preço, estoque e item que saiu do catálogo — e avisa na tela o que mudou (cartNotice). É esse efeito que faz o total na tela ser o que o banco vai gravar, e ele roda também no load() que a recusa por estoque dispara.
Finaliza pedido → create_pending_order (reserva estoque virtualmente, sem debitar de verdade — calcula assignment.quantity - reservas pendentes ainda dentro do prazo). Ela DEVOLVE o pedido gravado como jsonb ({order_id, total, discount_total, discount_units}), e é desse retorno que saem a mensagem do WhatsApp e o comprovante — nunca do carrinho, que pode estar com preço velho. O front manda um p_client_token (uuid gerado no primeiro envio): o mesmo token devolve o mesmo pedido em vez de criar outro, que é o que impede o timeout de 20s da loja de virar pedido duplicado. Tetos dentro da function, todos com espelho no front: nome 80, observação de entrega 300 (FREIGHT_MAX), 50 por item, 30 itens, 100 unidades e no máximo 3 pedidos pendentes por telefone naquele vendedor (muitos_pedidos_pendentes). Item repetido no payload é somado por produto ANTES da checagem de estoque — antes cada elemento era conferido sozinho e [{p,5},{p,5}] reservava 10 com 5 disponíveis.
Cliente compartilha via wa.me/?text=... sem número (deixa o WhatsApp dele escolher o contato — decisão consciente de privacidade, não expor telefone do vendedor). Esse passo é opcional pro sistema: o pedido já existe no banco antes dele.
Vendedor vê o pedido na SellerSalesPage (/minhas-vendas); admin, na aba "Pedidos pendentes" da SalesPage → confirma (confirm_order, debita estoque de verdade via create_sale) ou recusa (decline_order, libera a reserva virtual). As duas telas usam o MESMO hook (src/hooks/usePendingOrders.ts): confirmar e recusar são uma regra só, num lugar só.
Vendedor NÃO registra venda manual — a venda dele nasce de pedido do catálogo confirmado. O formulário manual (e a retirada de funcionário) é só do admin, na SalesPage. Por isso a SellerSalesPage vive FORA do AppLayout: ele tem uma tela só, e ela usa o tema .storefront em vez do Nocturne (ver src/pages/CLAUDE.md).
Confirmar não é clique único: abre um popover pedindo a forma de pagamento, e o valor pago é DERIVADO dela (pix/dinheiro ⇒ venda quitada; os quatro pendentes ⇒ zero recebido). Mesma regra do formulário de venda manual, de propósito — as duas portas de entrada de venda não podem divergir. O popover também aceita uma observação curta ("dia 20", "fiado") — texto livre para o acerto que não cabe no vocabulário fechado de forma de pagamento; ela não mexe em valor nenhum. Vai para sales.notes ANTES da referência do pedido (`<obs> · Pedido via catálogo #<id>`), porque a coluna de observações da SalesPage corta em 140px e o prefixo esconderia justamente o que foi escrito. Cortada em 80 caracteres nos dois lados (ORDER_NOTE_MAX no front, left(...,80) no banco). confirm_order(p_order_id uuid, p_payment_method text, p_notes text).
Prazo da reserva: 24h, em order_reservation_ttl(). Aplicado em dois níveis — como FILTRO no cálculo (create_pending_order e get_seller_catalog ignoram pendente vencido, então o estoque volta ao catálogo na hora) e como ESTADO, via expire_stale_orders(), que carimba 'expirada' só pra tirar o card da lista. Não há pg_cron: a varredura é chamada de dentro de create_pending_order e pelo poll da SalesPage. Como o cálculo já está certo sem ela, atrasar a varredura não prende estoque nenhum. confirm_order recusa pedido vencido (pedido_expirado) — confirmar depois do prazo debitaria estoque já prometido a outra pessoa.
Fidelidade
Conta unidades compradas (não pedidos), e só as que têm venda de verdade vinculada (order_items.sale_id IS NOT NULL — vendas manuais da SalesPage NÃO contam, só as do catálogo). A conta mora em customer_units(p_whatsapp), uma function só, porque o pedido e o cartão do checkout precisam EXATAMENTE do mesmo número.
Não é brinde, é desconto: a cada 6 unidades acumuladas (loyalty_cycle()), UMA sai por metade do preço — nunca por valor igual ou abaixo do preço de compra daquele produto; quando 50% bateria nesse piso, ela sai por custo + 15%. Preço de unidade premiada é SEMPRE em reais inteiros, nos dois caminhos, e SEMPRE arredondado para cima (ceil): preço de prêmio é número que a pessoa lê no card e o vendedor repete no WhatsApp, e para o mais perto quebraria a trava nos valores baixos, onde os 15% valem menos de R$ 0,50 (custo R$ 2,00 → 2,30 → round = 2, igual ao custo). A conta é loyalty_unit_price(sale_price, purchase_price), pura e travada em três cuidados: custo nulo ou zero não é margem infinita (vale os 50%), o preço premiado nunca passa o de venda (LEAST envolvendo o CASE inteiro, porque o ceil também estoura no ramo dos 50% num produto de R$ 0,50), e prêmio que não desconta NÃO é gasto — ele passa para o próximo item em vez de sumir. A comparação entre os dois caminhos testa o preço que VAI ser cobrado, já arredondado, não a metade exata.
O desconto é aplicado, não anunciado. create_pending_order calcula quantas unidades do pedido caem em posição múltipla do ciclo (contando histórico + carrinho) e grava a unidade premiada como linha própria em order_items, com o preço já descontado. Por isso não existe "controle de resgate": a linha É o comprovante e não tem como ser dada duas vezes. O prêmio cai na unidade MAIS BARATA do pedido (product_id desempata, como no ORDER BY do banco) — protege a margem e é a leitura que conversa com a trava do preço de compra.
A loja mostra o desconto ANTES de confirmar, e a prévia é a mesma conta: src/lib/cart-discount.ts (previewCartDiscount), com teste em src/test/cart-discount.test.ts. Ela lê loyalty_price e combo_price, colunas que get_seller_catalog devolve (o preço final, nunca o custo), e os números das regras vêm de get_store_rules / get_customer_loyalty — o 6 e o valor do combo não são repetidos no front de propósito. Quem manda é o banco: o comprovante e a mensagem do WhatsApp usam o total do retorno da function, não o da prévia.
Combo de modelo (migration 20260911120000): somadas as unidades de um MESMO modelo no pedido (marca+modelo normalizados por product_model_key, sabores misturados contam juntos), a partir de 2 todas saem R$ 7,00 mais baratas — combo_unit_price(sale_price, purchase_price), com a MESMA trava da fidelidade (nunca igual ou abaixo do custo; quando os R$ 7 bateriam ali, o preço vira custo + 15%; sem custo cadastrado o combo não passa da metade). Diferente do prêmio, ele preserva os centavos do preço cheio: é uma subtração que o cliente refaz de cabeça. Combo e fidelidade NÃO acumulam: a unidade premiada sai pelo melhor dos dois preços (na prática a metade), e as outras unidades do modelo ficam com o combo — create_pending_order calcula o preço BASE (cheio ou de combo) e só gasta o prêmio se ele for menor que esse base, senão o prêmio passa adiante intacto. Por isso a fila do prêmio é por preço base, não por preço cheio, no banco e no front. get_store_rules() devolve loyalty_cycle, combo_min_units, combo_discount e reservation_hours: é dela que saem os números que o card de promoção e o tira-dúvidas FALAM.
get_customer_loyalty(p_whatsapp) retorna: customer_name (só o PRIMEIRO nome), total_units, cycle_units, units_until_next_discount (nunca 0 — quando vale 1, a próxima unidade é a premiada), discounts_used, loyalty_tier. Saíram customer_id e whatsapp: a function é GRANT ... TO anon e devolvia dado de cliente que a tela nem lia. Faixas do tier: Fiel a partir de 20 unidades, Frequente a partir de 5, Novo abaixo disso — são sobre o tamanho da relação, não sobre o ciclo do desconto. O nome do tier é string literal dentro do corpo da function (não é enum nem tabela) e o front imprime cru — trocar o texto no SQL muda a loja na hora, sem mexer em .tsx. Só conta pedido com status 'confirmada'.
Efeito colateral consciente: quem recebe um preço vindo do piso consegue estimar o custo daquele produto dividindo por 1,15 — o arredondamento para inteiro devolve uma faixa em vez do número exato, mas ainda é uma pista. Vale só para item de margem curta e só para quem já é cliente. Se incomodar, o piso vira uma % do preço de VENDA e o custo some de qualquer conta.
Camada visual (Nocturne)
Nocturne é o tema do ERP. Tokens e classes moram em src/index.css (--nc-bg/rail/surface/text/divider/track, --nc-accent/alert/crit/profit/ok, .nc-card, .nc-row, .nc-rule-top, .nc-btn, .nc-input, .nc-hover, .nc-num, .nc-pill). A loja pública tem tema próprio (.storefront, documentado em src/pages/CLAUDE.md) — nada de lá vale aqui, e vice-versa.
--nc-ok (#81CFA8) é dinheiro que JÁ entrou: venda quitada, valor recebido, pix/dinheiro. Não é o mesmo papel do --nc-accent — o accent é o dinheiro todo (receita, o número grande do trilho, a série do gráfico), e o verde é o pedaço dele que já está na mão. Ao lado do --nc-alert ("falta receber") o par verde/laranja se lê antes do número. A matiz é a do --income que o app já tinha (hsl 152), trazida para o peso pastel dos outros tokens daqui: o #33CC7A original grita ao lado de um #85B7EB.
Todas as telas do ERP estão no Nocturne: Dashboard, Produtos, Entrada (/stock), Perdas (/losses), Vendas (/sales), Despesas (/expenses), Distribuição (/commissions, com o Extrato do vendedor), Insights (/insights) e Financeiro (/finance). A migração acabou — tela nova nasce no Nocturne, pelo esqueleto abaixo.
A raiz `/` não tem tela própria: cai em ProtectedRoutes pelo `/*` e vai para o login, ou para a tela do papel de quem já está logado. Havia ali um catálogo público (LandingPage) que ninguém usava, removido junto com o item "Catálogo" da sidebar. No banco saíram as três peças que só serviam a ele (migration 20260909120000): a function get_public_catalog(), o GRANT SELECT por coluna em products para anon e a policy "Public catalog read" — os três andavam juntos porque aquela function era SECURITY INVOKER e precisava de leitura direta na tabela. Depois disso o anon não tem acesso nenhum a public.products. A loja pública de verdade é /loja/:sellerId (SellerStorePage) e continua funcionando porque as três funções que ela usa (get_seller_catalog, create_pending_order, get_customer_loyalty) são SECURITY DEFINER e leem products por dentro.
.nc-pill é o selo de 10,5px com preenchimento a 14% da própria cor, e a cor vem da modificadora, não de quem usa: --paid (ok, verde) é dinheiro que entrou, --partial (alert) é o que falta, --open (crit) é o que não entrou nada, --mute é o que não tem informação. Situação da venda e forma de pagamento usam o MESMO vocabulário de tom de propósito — dois selos com a mesma cor têm que significar a mesma coisa em qualquer tela.
Esqueleto de tela migrada: raiz `<div className="nocturne flex flex-1 flex-col xl:flex-row xl:items-stretch">`, coluna principal (`flex-1 min-w-0 p-4 md:p-6 flex flex-col gap-4`, cabeçalho com sobretítulo accent + h1 de 22px + ação primária à direita) e um trilho `<aside>` de 312px no --nc-rail. No celular o trilho vem ANTES da lista (order-first) em toda tela cuja lista rola por telas — resumo embaixo de lista longa não é lido.
O trilho tem sempre a mesma gramática: sobretítulo terciário, UM número grande (AnimatedNumber), blocos separados por `Rule`, e uma lista curta de 6 linhas no fim. A barra dividida em duas cores só entra quando existe divisão REAL do total (recebido/a receber no Dashboard e em Vendas, custo/lucro no Produtos, casa/vendedores nas Perdas). Na Entrada não tem barra de propósito: não havia divisão de verdade para mostrar, e uma barra inventada mentiria. Nas abas Retiradas e Pedidos da SalesPage também não, e nas Despesas também não — despesa se reparte em N categorias, não em duas metades; a repartição real fica na lista do fim, com a participação de cada uma.
Bloco do trilho que NÃO segue o filtro da tela precisa dizer isso na própria linha ("Não segue o filtro: …"), como o "A caminho" da Entrada e o "Ritmo do mês" das Despesas. O Ritmo compara com o mesmo TRECHO do mês passado (até o mesmo dia), não com o mês fechado: dia 3 contra um mês inteiro diria todo começo de mês que a despesa despencou. Só o aumento ganha cor (--nc-crit); gastar menos NÃO vira --nc-ok, porque aquele verde é dinheiro que entrou.
Tela com abas: o trilho ACOMPANHA a aba ativa (Vendas tem receita, Retiradas tem valor retirado, Pedidos tem valor reservado). Um resumo de vendas parado ao lado da lista de pedidos pendentes falaria de outra coisa que não a tela na frente. O `Tabs` do Radix embrulha só a coluna principal; o `<aside>` fica fora dele e lê o estado, porque o trilho não é conteúdo de aba nenhuma.
Peça usada por duas telas mora em src/components/nocturne e as duas importam — ninguém copia estilo de tela em tela. Hoje: NcButton, NcSheetHeader, SegmentedChips, NcTabsList, Rule, EYEBROW. (SegmentedChips nasceu dentro do Dashboard como PeriodChips e só virou peça compartilhada quando a Entrada precisou do mesmo filtro; virou SegmentedChips quando a Distribuição usou a mesma peça para filtrar o histórico por TIPO — o desenho nunca foi sobre período, e nome que promete data manda a próxima tela desenhar o seu. NcTabsList saiu da SalesPage quando o Extrato do vendedor precisou das mesmas abas.)
Um assunto, um painel. Tudo o que se faz com um vendedor acontece DENTRO do painel dele: o resumo fica de pé e o formulário (pagar comissão, receber dívida, lançar dívida) abre por baixo, com o rodapé virando o botão de confirmar. Antes eram quatro painéis que fechavam um para abrir o outro, cada um repetindo o cabeçalho do vendedor, e quem estava pagando não via mais o saldo que ia pagar. Depois de registrar, o painel VOLTA ao resumo em vez de fechar: o saldo recalculado é a confirmação. Mesma regra em Movimentar estoque — atribuir e transferir eram dois painéis para o mesmo movimento, e a diferença (de onde a unidade sai) cabe num campo, como a origem da perda em /losses.
Progresso do vendedor é "18/21 un. para 15%", não barra: a meta da comissão é um degrau em número de unidades (10 → 12,5% → 15%), e barra some com o número que ele persegue. Barra fica para divisão de total (o lucro que se reparte entre vendedores e sócios, no trilho) e para alvo de sócio (retirado / falta / excedente).
Formulário de registro abre como PAINEL LATERAL (Sheet), não como diálogo no meio da tela: NcSheetHeader no topo, corpo em seções com sobretítulo terciário, e rodapé no --nc-rail com o resumo do que vai acontecer à esquerda e o NcButton solid à direita. Diálogo central ficou só para edição pontual e confirmação (ProductsPage).
Ao migrar uma tela: (1) adicione a rota em fullBleedRoutes no AppLayout, senão ela chega com o padding e o max-w-7xl do layout antigo e o trilho não encosta na borda; (2) repita className="nocturne" em TODO conteúdo portado pelo Radix (SheetContent, DialogContent, SelectContent) — o portal sai da árvore da página e os tokens não chegam por herança, mesma regra que a loja documenta; (3) ícone de tela vem do lucide-react (o phosphor é só do app-shell no AppLayout, onde os glifos vieram do mockup).
Gotchas de Postgres já pegos (não repetir)
FOR UPDATE não pode ser usado junto com função de agregação (SUM, COUNT) na mesma query — dá erro de sintaxe. Padrão correto: travar as linhas numa subquery, agregar por fora dela.
Grant de coluna, não só RLS: products tem REVOKE SELECT ON products FROM authenticated seguido de GRANT SELECT (lista de colunas específicas). RLS sozinho não basta — se adicionar coluna nova numa tabela com esse padrão, sempre dar GRANT SELECT (nova_coluna) ON tabela TO authenticated na mesma migration, ou a consulta inteira falha silenciosamente (o client não trata erro em algumas queries, então parece "dado sumiu" quando na verdade é permissão faltando).
Ao mudar o formato de retorno de uma function existente (RETURNS TABLE(...) com colunas diferentes), CREATE OR REPLACE falha com cannot change return type. Precisa DROP FUNCTION nome(tipos_dos_parametros) antes de recriar. O mesmo vale pra mudar a lista de parâmetros: sem o DROP ficam duas versões coexistindo e a antiga continua sendo chamada.
supabase/migrations/ pode estar ATRASADO em relação ao banco — coisa aplicada direto no SQL Editor não vira arquivo sozinha. Quem reflete o banco real é src/integrations/supabase/types.ts (gerado). Antes de mexer numa function existente, comparar os dois; se divergirem, recuperar a versão viva com SELECT prosrc FROM pg_proc WHERE proname='<nome>' e commitar ela ANTES de mudar qualquer coisa. Já aconteceu com get_customer_loyalty (migration tinha a versão por pedido, banco rodava a por unidade — um db reset teria quebrado o checkout).
Forma de pagamento tem vocabulário fechado: pix, dinheiro, pix_pendente, dinheiro_pendente, dinheiro_com_vendedor, pendente. Qualquer outro valor gravado em sales.payment_method vira undefined no mapSale do StoreContext e a coluna aparece como "—" na tela, sem erro nenhum. (confirm_order gravava 'combinado' e por isso todo pedido de catálogo aparecia sem forma de pagamento.)
Movimento: ao abrir uma tela quem sobe é o BLOCO INTEIRO, uma vez só — o `PageTransition` (fade + 6px). Linha, card e texto NÃO têm entrada própria: `listItem` tem `hidden` igual a `visible`, e `Stagger`/`StaggerItem`/`StaggerAuto` são containers comuns (guardam o className e o AnimatePresence dos filhos, não orquestram cascata). Cascata dava a impressão de a tela montar aos pedaços, e em lista longa parecia carregamento lento de um dado que já estava na mão. O que continua animando é reação a clique: a SAÍDA da linha excluída (`listItem.exit`), a altura que abre, o realce que desliza. A loja pública (.storefront) ainda tem a entrada em cascata própria, documentada em src/pages/CLAUDE.md.
Insights mede COBERTURA (dias de estoque), não giro. Cobertura = estoque de hoje ÷ (unidades vendidas ÷ dias JÁ CORRIDOS do período) — no mês em curso o divisor é até hoje, não até o dia 30, senão o ritmo sai um terço do real e o aviso de reposição chega tarde no único mês em que serve. O giro antigo (vendidos ÷ estoque médio) foi removido por três motivos, e nenhum deles se conserta com ajuste fino: tinha o estoque no divisor e por isso elegia como "melhor" o modelo que estava zerando (Infinity quando o estoque médio era 0, ordenado como 999); reconstruía o estoque inicial para trás desfazendo entradas/vendas/perdas, conta que a edição manual de `stock` na ProductsPage fura em silêncio; e era uma razão sem unidade nem tempo. Não traga o giro de volta.
Estoque mínimo por modelo compara a soma do estoque com a SOMA dos mínimos dos sabores. Comparar com o MAIOR mínimo dava modelo "saudável" com seis de oito sabores zerados — por isso a linha também mostra quantos sabores estão em falta.
Número que aparece em duas telas é a MESMA conta nas duas, e a formatação também: real sai de src/lib/currency.ts (formatCurrency / formatCurrencyShort, formatadores criados uma vez), como o intervalo de datas sai de src/lib/date-utils.ts. No Financeiro isso vale para "ainda a devolver": principal + juro que falta, o mesmo número no cabeçalho da seção, na linha do empréstimo e no trilho. O razão carrega só o PRINCIPAL em loan_delta (o juro entra por accumulated_profit_delta), então o trilho mostra as duas metades embaixo do número — e o formulário de pagamento sugere cada uma no seu campo, porque jogar o total no campo de principal levava o saldo do razão a negativo. Ticket médio é faturamento ÷ quantidade de vendas (Dashboard `computeStats` e Vendas `totals.ticket`). O Dashboard fazia recebido ÷ total de vendas: misturava dinheiro só das vendas quitadas com a contagem de todas, então o número caía justamente no mês que vendeu bem e recebeu devagar. Recebido é assunto do par recebido/a receber, não do ticket.
`npm run build` no Windows CORROMPE supabase/functions/mcp/index.ts. O mcpPlugin() do @lovable.dev/mcp-js (em vite.config.ts) regera esse arquivo a cada build, e aqui ele emite `import mcp from "npm:C:\Users\...\src\lib\mcp\index.ts"` — caminho absoluto do Windows dentro de um especificador `npm:`, que o Deno não resolve. Na Lovable (Linux) sai o bundle inteiro, correto. Depois de qualquer build local, confira `git status` e descarte a mudança nesse arquivo com `git checkout -- supabase/functions/mcp/index.ts`. NUNCA commite a versão gerada aqui: ela quebra a edge function em produção.
Gotchas de front já pegos (não repetir)
AnimatePresence com mode="wait" NÃO pode envolver o <Routes>. Foi a causa do bug "troquei de página e a tela não apareceu; só depois de clicar no ícone de novo". Dois motivos: o filho que sai não segura a tela antiga (o <Routes> lê a localização do contexto e re-renderiza a tela NOVA lá dentro, então cada navegação montava a página de destino duas vezes), e a fila do mode="wait" trava se qualquer re-render do pai cair dentro da janela da saída — o elemento novo monta e fica parado no initial, no DOM e em opacity: 0. Hoje o PageTransition é só um motion.div com key={pathname}, sem AnimatePresence. Travado em src/test/page-transition.test.tsx.
Botão que só existe quando há filtro ativo, numa linha flex ao lado de uma busca com flex-1, faz a busca crescer e encolher a cada clique. Mantenha o botão SEMPRE montado e esconda com `invisible` + `disabled` — o espaço fica reservado e nada se mexe. (Produtos ainda tem esse solavanco, ver roadmap.)
Ação que só aparece no hover da linha não existe no toque, e quem não passa o mouse exatamente ali nunca descobre que ela existe. Quando a ação tem um ESTADO equivalente já visível na linha, o estado é que vira o botão, em vez de um botão fantasma ao lado: na SalesPage o selo "Aberto" é o alvo, e no hover (ou com o popover aberto, via `data-state`) ele vira o selo "Pago" que o clique produz — o hover é a pré-visualização do resultado. Os dois rótulos ficam empilhados na MESMA célula de grid (`col-start-1 row-start-1`), então a pílula nasce com a largura do maior e não muda de tamanho ao trocar de texto. Excluir/editar continuam no hover: para eles não existe estado visível que sirva de alvo.
O que falta (roadmap)
Upload de foto real (hoje é só colar link; sem Supabase Storage ainda). Enquanto isso, a loja não serve a URL crua: ela passa por um redimensionador público (src/lib/image-proxy.ts, wsrv.nl) que devolve a foto no tamanho da tela e em WebP — a original de 2MB virava 3,7KB na miniatura e ~112KB no card, medido. O banco continua guardando a URL original, o proxy é só leitura, e o onError da ProductMedia cai de volta na original se o serviço falhar. É dependência de terceiro assumida de propósito: no dia do Storage, PROXY_HOST = null desliga tudo.
Tela de listagem de clientes (dado já existe em customers, falta a UI).
Checkout com pagamento direto (Stripe) — adiado conscientemente, fluxo atual é WhatsApp + confirmação manual.
Rate limit de verdade em create_pending_order: hoje o freio é o teto de 3 pedidos pendentes por telefone/vendedor mais os tetos de tamanho do payload — não é rate limit, é limite de estrago por requisição. get_customer_loyalty continua aberta a anon sem freio nenhum: ela devolve menos dado que antes (primeiro nome e números), mas ainda confirma se um telefone é cliente.
Tela de histórico de pedidos: a UI só consulta status 'pendente'. Confirmada, recusada e expirada existem no banco e não aparecem em lugar nenhum.
Desempenho da lista de Vendas: a tela monta uma linha por venda, sem virtualização nem paginação, e o filtro "Tudo" já trava perceptivelmente ao carregar. Paliativo em pé: Vendas e Entrada abrem no mês corrente (DEFAULT_PRESET em cada tela, intervalo vindo de currentMonthRange() em src/lib/date-utils.ts, o mesmo que o chip "Mês" produz) e o "Limpar" volta para o mês, não para "Tudo" — o botão devolve a tela ao estado em que ela abriu. Por isso o período só conta em hasActiveFilters quando difere do padrão. A correção é virtualizar a lista (ou paginar no banco) — enquanto ela não vem, não troque o padrão de volta para "Tudo". O StoreContext também carrega sales inteiro na memória, então o mesmo teto vale para Dashboard e Distribuição.
Empréstimo e aporte não têm edição — só criar e excluir. updateLoan existe no StoreContext e nenhuma tela chama.
Produtos ainda tem o solavanco de largura no card de filtro — o "Limpar" que monta e desmonta e o botão que troca de rótulo entre "Ocultar zerados" e "Mostrar zerados (N)".
